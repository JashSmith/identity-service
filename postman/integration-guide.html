راهنمای کار با سرویس هویت (Identity Facade)

این راهنمای عملی شش مرحلهٔ کار با Identity Facade را توضیح می‌دهد: احراز هویت، سرویس‌های کاربران، نقش‌های کسب‌وکاری، Scopeها به‌عنوان attribute، ساخت کاربر Scopeدار و مدیریت رجیستری Scope. هر نمونه با اجرای واقعی روی استک docker تست شده و خروجی واقعی آن درج شده است.

اصل معماری: Keycloak مالک کاربران، گذرواژه‌ها، نشست‌ها، گروه‌ها، نقش‌ها و صدور JWT است. Facade فقط پروکسی، اعتبارسنجی، نرمال‌سازی و مدیریت مجوزها را انجام می‌دهد و هیچ توکنی تولید نمی‌کند. مصرف‌کننده‌ها آدرس Keycloak را نمی‌دانند؛ فقط به Facade وصل می‌شوند.
منبع حقیقت: همهٔ دادهٔ احراز هویت در Keycloak است. نقش تجاری = Group، مجوز = Client Role روی کلاینت همان سرویس، Scope = attribute روی کاربر/گروه، و تعریف Scopeها در گروه پیکربندی iam-scope-registry. دیتابیس Oracle فقط متادیتای کلیدهای امضا را نگه می‌دارد.

۱. ورود، احراز هویت، Refresh، Introspect و خروج

همهٔ مسیرهای زیر پروکسی Keycloak هستند؛ Facade هیچ توکنی نمی‌سازد و گذرواژه را ذخیره نمی‌کند.

۱.۱ ورود کاربر (Password Grant)

curl -s -X POST http://localhost:5080/api/identity/auth/login \ -d "grant_type=password" \ -d "client_id=identity-facade" \ -d "client_secret=facade-development-only" \ -d "username=admin" \ -d "password=admin"

پاسخ واقعی (توکن‌ها کوتاه شده‌اند):

{ "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCIgOiAiSldUIiwia2lkIiA6...", "refresh_token": "eyJhbGciOiJIUzUxMiJ9...", "expires_in": 300, "token_type": "Bearer" }
چطور توکن را نگه دارید: فقط access_token را در حافظهٔ کوتاه‌مدت نگه دارید و در هدر Authorization: Bearer بگذارید. refresh_token را امن ذخیره کنید. هیچ‌کدام را در لاگ یا URL ننویسید.
# ذخیرهٔ توکن در متغیر محیطی برای دستورات بعدی TOKEN=$(curl -s -X POST http://localhost:5080/api/identity/auth/login \ -d "grant_type=password&client_id=identity-facade&client_secret=facade-development-only&username=admin&password=admin" \ | python -c "import json,sys; print(json.load(sys.stdin)['access_token'])")

۱.۲ ورود سرویس (Client Credentials)

برای ارتباط ماشین‌به‌ماشین، بدون نام کاربری. همان مسیر ورود با grant_type=client_credentials:

curl -s -X POST http://localhost:5080/api/identity/auth/login \ -d "grant_type=client_credentials" \ -d "client_id=order-service" \ -d "client_secret=order-service-development-only"
محدودیت مهم: Service Account نمونه فقط مجوز Identity.Permissions.Register دارد؛ یعنی ثبت Manifest مجاز است ولی خواندن دادهٔ کسب‌وکار نه. برای دسترسی بیشتر باید مجوزها صریحاً به نقش یا گروه آن سرویس داده شود.

۱.۳ اطلاعات کاربر جاری

curl -s http://localhost:5080/api/identity/me -H "Authorization: Bearer $TOKEN"

پاسخ واقعی برای admin:

{ "userId": "d05b0be6-e42c-4a0e-b195-162f1ba651df", "username": "admin", "roles": [], "permissions": [ "identity.users.manage", "identity.roles.manage", "identity.scopes.manage", "identity.users.read", "identity.roles.read", "identity.scopes.read", "Identity.Users.Read", "Identity.Roles.Read", "Identity.Permissions.Read", "Identity.Permissions.Register", "Identity.Keys.View", "Identity.Keys.Generate" ], "sessionId": "42144108-9af6-ba0b-0445-d4e339b8d4cb" }
دو دستهٔ نام مجوز: مجوزهای Identity.* (با حرف بزرگ) مربوط به ماژول مدیریت کلید و Directory قدیمی‌اند؛ مجوزهای identity.* (با حرف کوچک) مجوزهای مدیریتی خود Facade برای کاربر/نقش/Scope هستند و همان‌هایی‌اند که Endpointها با RequireAuthorization چک می‌کنند. کاربر admin عضو گروه super-admins است و هر دو دسته را دارد.

۱.۴ تازه‌سازی توکن (Refresh)

curl -s -X POST http://localhost:5080/api/identity/auth/refresh \ -d "grant_type=refresh_token" \ -d "client_id=identity-facade" \ -d "client_secret=facade-development-only" \ -d "refresh_token=$REFRESH_TOKEN"

پاسخ همان ساختار ورود است، با توکن‌های تازه. Keycloak در این realm چرخش Refresh Token را فعال دارد، پس همیشه مقدار برگشتی را جایگزین قبلی کنید.

کی Refresh لازم است: پس از تغییر مجوز یا Scope یک کاربر، توکن فعلی تغییر نمی‌کند. با Refresh یا ورود مجدد، توکن تازه شامل مقادیر جدید است (تأییدشده در تست).

۱.۵ اعتبارسنجی توکن (Introspect)

curl -s -X POST http://localhost:5080/api/identity/auth/introspect \ -d "client_id=identity-facade" \ -d "client_secret=facade-development-only" \ -d "token=$TOKEN"

پاسخ واقعی طبق RFC 7662:

{ "active": true, "sub": "d05b0be6-e42c-4a0e-b195-162f1ba651df", "client_id": "identity-facade", ... }
تفاوت با اعتبارسنجی محلی: سرویس‌ها در حالت عادی توکن را محلی با JWKS اعتبارسنجی می‌کنند و به این Endpoint نمی‌زنند. Introspect فقط برای عملیات حساس (پرداخت، حذف، تغییر مالکیت) لازم است که «همین لحظه باطل نشده باشد» اهمیت دارد.

۱.۶ خروج و ابطال نشست (Logout)

curl -s -X POST http://localhost:5080/api/identity/auth/logout \ -d "client_id=identity-facade" \ -d "client_secret=facade-development-only" \ -d "refresh_token=$REFRESH_TOKEN"

پاسخ واقعی:

{ "success": true }

Facade ابتدا Logout Keycloak را صدا می‌زند و در صورت شکست، به Endpoint ابطال (Revoke) می‌رود. پس از خروج، توکن‌های ذخیره‌شده را از حافظه پاک کنید.

خروج Access Token را فوراً باطل نمی‌کند: Access Token تا انقضا (حداکثر ۵ دقیقه) با JWKS معتبر می‌ماند؛ آنچه باطل می‌شود نشست و Refresh Token است. برای ابطال فوری لازم است عمر توکن کوتاه بماند (همین ۳۰۰ ثانیه) یا Introspect استفاده شود.

۱.۷ Discovery و JWKS (برای مصرف‌کننده‌ها)

curl -s http://localhost:5080/.well-known/openid-configuration curl -s http://localhost:5080/api/identity/oidc/jwks

Facade سند Discovery را از Keycloak عبور می‌دهد و فقط jwks_uri را به خودش تغییر می‌دهد. issuer و بقیهٔ Endpointها دست‌نخورده می‌مانند تا توکن واقعی Keycloak بدون تغییر اعتبارسنجی شود. مصرف‌کننده باید AcceptIssuerFromDiscovery = true را فعال کند، چون Authority آدرس Facade است اما Issuer متعلق به Keycloak.

۲. سرویس‌های کاربران و نقش‌ها

این مسیرها Directory خواندنی روی Keycloak هستند و با Bearer Token و مجوز خواندن کار می‌کنند.

مسیرمجوز لازمکاربرد

GET /api/identity/users/{id}Identity.Users.Readجزئیات یک کاربر
GET /api/identity/users/{id}/rolesIdentity.Users.Readنقش‌های کاربر

۲.۱ فهرست کاربران

curl -s "http://localhost:5080/api/identity/users?page=1&pageSize=20" \ -H "Authorization: Bearer $TOKEN"

پاسخ واقعی (صفحه‌بندی‌شده):

{ "items": [ { "id": "d05b0be6-...", "username": "admin", "displayName": "Admin User", "enabled": true, "attributes": {} } ], "page": 1, "pageSize": 20, "total": null }
محدودیت صفحه: pageSize بین ۱ تا ۱۰۰ محدود (Clamp) می‌شود. search روی نام کاربری و ایمیل جستجو می‌کند. total عمداً null است چون Keycloak شمارش کل را ارزان ارائه نمی‌دهد.

۲.۲ مجوزهای مؤثر یک کاربر

curl -s http://localhost:5080/api/identity/users/{userId}/permissions \ -H "Authorization: Bearer $TOKEN"
نکتهٔ مهمی که در تست کشف شد: Endpoint نقش‌های Keycloak (/users/{id}/role-mappings) فقط نقش‌های مستقیم را برمی‌گرداند. در مدل ما مجوزها از طریق عضویت در گروه (نقش کسب‌وکاری) به کاربر می‌رسند، پس این Endpoint قبلاً خالی برمی‌گشت. اکنون Facade نقش‌های مستقیم را با نقش‌های ارثی از گروه‌ها (هم Realm Role و هم Client Role همهٔ کلاینت‌ها) ترکیب می‌کند.

پاسخ واقعی برای کاربری که عضو گروه SeniorAccountant است:

[ { "name": "Orders.View", "description": "Orders.View", "deprecated": false }, { "name": "Orders.Create", "description": "Orders.Create", "deprecated": false }, { "name": "Orders.Approve", "description": "Orders.Approve", "deprecated": false }, { "name": "Orders.Export", "description": "Orders.Export", "deprecated": false } ]

۲.۳ کاتالوگ مجوزهای ثبت‌شده

curl -s "http://localhost:5080/api/identity/permissions?serviceId=order-service" \ -H "Authorization: Bearer $TOKEN"

پاسخ واقعی (بخشی از ۱۰ مجوز ثبت‌شده توسط order-service):

[ { "name": "Orders.View", "serviceId": "order-service", "deprecated": false }, { "name": "Orders.Create", "serviceId": "order-service", "deprecated": false }, { "name": "Orders.Cancel", "serviceId": "order-service", "deprecated": false }, { "name": "Orders.Invoices.Issue", "serviceId": "order-service", "deprecated": false }, { "name": "Orders.Reports.Export", "serviceId": "order-service", "deprecated": false } ]
رفتار مهم پس از راه‌اندازی مجدد: کاتالوگ مجوزها در حافظهٔ Facade است. پس از Restart، تا وقتی سرویس‌ها دوباره Manifest خود را ثبت نکنند این فهرست خالی است. به همین دلیل اعتبارسنجی «آیا این مجوز وجود دارد؟» عمداً به Keycloak (منبع حقیقت) سپرده شده نه به این کاتالوگ حافظه‌ای؛ وگرنه پس از هر Restart، اختصاص مجوزهای کاملاً معتبر با خطای «وجود ندارد» رد می‌شد.

۳. ساخت نقش کسب‌وکاری و اعطای دسترسی

نقش کسب‌وکاری در Keycloak یک Group است و مجوزها Client Role روی کلاینت سرویس مربوطه. اختصاص مجوز به نقش یعنی Map کردن Client Role روی آن Group.

۳.۱ ساخت نقش (مثلاً حسابدار اصلی)

cat > role.json <<'EOF' { "name": "SeniorAccountant", "description": "حسابدار اصلی", "permissions": ["Orders.View", "Orders.Create", "Orders.Approve"] } EOF curl -s -X POST http://localhost:5080/api/identity/business-roles \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json; charset=utf-8" \ --data-binary @role.json

پاسخ واقعی (HTTP 201 Created):

{ "name": "SeniorAccountant", "description": "حسابدار اصلی", "composite": true, "permissions": ["Orders.Approve", "Orders.Create", "Orders.View"] }
تلهٔ رمزگذاری فارسی (مهم): اگر بدنهٔ JSON را با -d '{"description":"حسابدار اصلی"}' داخل خود خط فرمان بنویسید، کنسول ویندوز آن را با Code Page محلی (نه UTF-8) به curl می‌دهد و سرور خطای Cannot transcode invalid UTF-8 JSON text با HTTP 400 برمی‌گرداند. همیشه بدنه را در فایل UTF-8 بگذارید و با --data-binary @file بفرستید، یا از Postman/Scalar استفاده کنید. این محدودیت خط فرمان است، نه ایراد سرویس.

۳.۲ خواندن نقش و مجوزهای مؤثر

curl -s http://localhost:5080/api/identity/business-roles/SeniorAccountant \ -H "Authorization: Bearer $TOKEN" curl -s http://localhost:5080/api/identity/business-roles/SeniorAccountant/effective-permissions \ -H "Authorization: Bearer $TOKEN"

پاسخ واقعی:

{ "role": "SeniorAccountant", "permissions": ["Orders.Approve","Orders.Create","Orders.Export","Orders.View"] }

«مؤثر» یعنی اجتماع Client Roleهای همهٔ کلاینت‌ها + Realm Roleهای Map شده + گسترش نقش‌های ترکیبی (Composite).

۳.۳ افزودن و حذف مجوز

# افزودن cat > perms.json <<'EOF' { "permissions": ["Orders.Export", "Orders.Cancel"] } EOF curl -s -X POST http://localhost:5080/api/identity/business-roles/SeniorAccountant/permissions \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ --data-binary @perms.json # حذف curl -s -X DELETE http://localhost:5080/api/identity/business-roles/SeniorAccountant/permissions/Orders.Cancel \ -H "Authorization: Bearer $TOKEN"

پاسخ واقعی حذف (HTTP 200) — توضیح فارسی و بقیهٔ مجوزها حفظ شده‌اند:

{ "name": "SeniorAccountant", "description": "حسابدار ارشد — دسترسی سفارش‌ها", "composite": true, "permissions": ["Orders.Approve", "Orders.Create", "Orders.Export", "Orders.View"] }

۳.۴ ویرایش توضیح نقش

cat > role-update.json <<'EOF' { "description": "حسابدار ارشد — دسترسی سفارش‌ها" } EOF curl -s -X PUT http://localhost:5080/api/identity/business-roles/SeniorAccountant \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ --data-binary @role-update.json
نکتهٔ مهم دربارهٔ Attributeها: در Keycloak، PUT روی یک Group کل مجموعهٔ Attributeها را جایگزین می‌کند. نسخهٔ قبلی فقط description و authz.allowed-scopes را نگه می‌داشت؛ یعنی ویرایش توضیح، Scopeهای سطح گروه (authz.scope.*) را پاک می‌کرد. اکنون همهٔ Attributeهای موجود خوانده و حفظ می‌شوند و فقط description تغییر می‌کند.

۳.۵ حذف نقش

curl -s -X DELETE http://localhost:5080/api/identity/business-roles/SeniorAccountant \ -H "Authorization: Bearer $TOKEN" # 204 No Content

اگر کاربری هنوز عضو نقش باشد، حذف با HTTP 400 و پیام روشن رد می‌شود:

{ "code": "validation_error", "message": "Cannot delete business role 'SeniorAccountant': still assigned to 2 user(s). Remove scoped assignments first." }

۳.۶ سه ایرادی که در این مرحله پیدا و رفع شد

نشانهٔ ظاهریعلت ریشه‌ایوضعیت
ساخت نقش 201 می‌داد ولی permissions: [] و description: null برمی‌گشت۱) مجوزها به Client Role تبدیل می‌شدند ولی مسیر خواندن یک UUID را به‌جای clientId جستجو می‌کرد، پس هیچ‌وقت تطبیق نمی‌شد. ۲) جستجوی گروه در Keycloak به‌صورت پیش‌فرض «خلاصه» است و Attributeها را برنمی‌گرداند.رفع شد
اختصاص مجوز با «Permission 'Orders.View' does not exist.» رد می‌شداعتبارسنجی از کاتالوگ حافظه‌ای می‌خواند که پس از Restart خالی است؛ در حالی که مجوز واقعاً در Keycloak وجود داشت.رفع شد
حذف مجوز خطا می‌دادهمان باگ UUID/clientId در مسیر حذف.رفع شد

۴. Scope به‌عنوان دادهٔ Attributeشده

Scope یعنی محدودیت داده‌محور: «این کاربر فقط در تهران-۲ کار می‌کند». Scopeها نه در دیتابیس Facade، بلکه به‌صورت attribute روی کاربر و گروه در Keycloak نگه داشته می‌شوند و از آنجا به توکن و سپس به فیلتر سطح دیتابیس در سرویس مصرف‌کننده می‌رسند.

۴.۱ مدل داده

مفهوممحل ذخیره در Keycloakمثال
تعریف Scope (چه کلیدهایی مجازند)Attribute گروه iam-scope-registry با کلید scope.<key>scope.region = JSON شامل displayName، isActive، valueType
نگاشت منبع به Scopeهمان گروه، کلید resource.<name>resource.Orders = ["region","branch","warehouse","customer"]
مقادیر مجاز برای یک نقشAttribute گروه نقش: authz.allowed-scopes["region","branch"]
مقدار واقعی کاربرAttribute کاربر: authz.scope.<key> (چندمقداری)authz.scope.region = ["tehran-2"]
مقدار سطح گروه (مشترک همهٔ اعضا)Attribute گروه: authz.scope.<key>authz.scope.region = ["tehran-1"]
قانون مؤثر: Scopeهای مؤثر کاربر = اجتماع (Union) مقادیر گروه و کاربر برای هر کلید. اگر گروه SeniorAccountant مقدار region=tehran-1 داشته باشد و خود کاربر region=tehran-2، نتیجه ["tehran-1","tehran-2"] است. این رفتار در تست تأیید شد.

۴.۲ خواندن و نوشتن Scope یک کاربر

# خواندن curl -s http://localhost:5080/api/identity/users/{userId}/scoped-access \ -H "Authorization: Bearer $TOKEN" # جایگزینی کامل (Replace) cat > scopes.json <<'EOF' { "assignments": [ { "role": "SeniorAccountant", "scopes": { "region": ["tehran-2"], "branch": ["b-3"] } } ] } EOF curl -s -X PUT http://localhost:5080/api/identity/users/{userId}/scoped-access \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ --data-binary @scopes.json # افزودن یک تخصیص (بدون پاک کردن قبلی‌ها) curl -s -X POST http://localhost:5080/api/identity/users/{userId}/scoped-assignments \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ --data-binary @scopes.json # حذف تخصیص یک نقش curl -s -X DELETE http://localhost:5080/api/identity/users/{userId}/scoped-assignments/SeniorAccountant \ -H "Authorization: Bearer $TOKEN"

پاسخ واقعی PUT:

{ "userId": "bd501d92-...", "assignments": [ { "role": "SeniorAccountant", "scopes": { "region": ["tehran-2"], "branch": ["b-3"] } } ] }
فرم کوتاه (Scalar) هم مجاز است: می‌توانید به‌جای آرایه یک رشته بدهید؛ خودکار به آرایه نرمال می‌شود:
{ "role": "SeniorAccountant", "scopes": { "test-key": "items-1" } } ≡ { "role": "SeniorAccountant", "scopes": { "test-key": ["items-1"] } }
مقادیر تکراری حذف، مرتب و Trim می‌شوند. پس برای افزودن Scope جدید نیازی به تغییر DTO نیست.

۴.۳ چطور در توکن ظاهر می‌شود

Client Scope authz-scopes برای هر کلید یک Mapper دارد که attribute authz.scope.<key> را به Claim تبدیل می‌کند.

مهم — نقطه در نام Claim باعث تودرتو شدن می‌شود: Keycloak نقطهٔ داخل claim.name را به ساختار تودرتوی JSON تبدیل می‌کند. پس Claim به‌صورت کلید مسطح "authz.scope.region" نمی‌آید، بلکه این‌طور است:

Payload واقعی توکن کاربر تست‌شده:

{ "sub": "84b48d80-79b9-4a16-8fdb-b41dc1d7232c", "preferred_username": "sara-tax", "authz": { "scope": { "region": ["tehran-2", "tehran-1"], "branch": ["b-3"] } }, "iam_access": "[{\"role\":\"SeniorAccountant\",\"scopes\":{\"branch\":[\"b-3\"],\"region\":[\"tehran-2\"]}}]", "permissions": ["Orders.Approve","Orders.Create","Orders.Export","Orders.View"] }

بنابراین در کد مصرف‌کننده باید authz → scope → region خوانده شود، نه یک کلید مسطح.

۴.۴ دو مسیر خواندن در سرویس مصرف‌کننده

مسیرمزیتمحدودیت
Claim iam_access (رشتهٔ JSON شامل نقش‌ها)بدون تماس شبکه‌ای؛ نقش‌به‌نقش تفکیک شدهبرای بار بزرگ ممکن است از توکن حذف شود؛ در آن صورت EnsureLoadedAsync از Facade می‌خواند
Claimهای authz.scope.* (تودرتو)مستقیم از توکن، بدون تجزیهٔ JSON دستیتجمیع‌شده است (تفکیک نقش ندارد)
// در سرویس مصرف‌کننده builder.Services.AddCompanyAccessContext(o => o.FacadeBaseUrl = configuration["Identity:AccessContext:FacadeBaseUrl"]); // در Endpoint await access.EnsureLoadedAsync(ct); var regions = access.GetScopeValues("region"); // ["tehran-1","tehran-2"] bool ok = access.HasPermission("Orders.View", "region", "tehran-2");

۴.۵ فیلتر سطح دیتابیس

query = await scopeFilter.ApplyAsync(query, effectiveScopes, ResourceKeys.Orders, ct);

رفتار Deny-by-default است: اگر نگاشت منبع وجود نداشته باشد یا Handler ثبت نشده باشد یا کاربر Scope لازم را نداشته باشد، نتیجه خالی است. چند مقدار داخل یک کلید با OR و چند کلید مختلف با AND ترکیب می‌شوند.

نتیجهٔ واقعی تست روی order-service — کاربری با region=tehran-1 (از گروه) و region=tehran-2 (از خودش):

GET /api/orders/scoped [ { "id": "ord-1", "region": "tehran-1" }, { "id": "ord-2", "region": "tehran-2" } ] ← فقط دو سفارش مجاز؛ ord-3 (global) حذف شد

و بررسی تک‌تک (GET /api/orders/{id}/scoped-check?region=...):

region=tehran-2 (مجاز) → 200 + بدنهٔ سفارش region=tehran-1 (غیرمجاز) → 403
AND بین ابعاد را جدی بگیرید: اگر کاربری هم region و هم branch داشته باشد و هر دو برای آن منبع نگاشت شده باشند، هر دو فیلتر اعمال می‌شوند (AND). در نمونهٔ order-service فیلتر branch برای ساده‌سازی روی همان فیلد Region عمل می‌کند؛ پس دادن branch=b-3 نتیجه را خالی می‌کند و Endpoint 403 برمی‌گرداند. این رفتار درستِ Deny-by-default است، نه باگ — اما در طراحی ابعاد Scope دقت کنید که ابعاد واقعاً مستقل باشند.

۴.۶ دو ایراد مهمی که در این مرحله پیدا و رفع شد

نشانهٔ ظاهریعلت ریشه‌ایوضعیت
نوشتن Scope 204/200 می‌داد ولی Attribute در Keycloak ذخیره نمی‌شد و Claim خالی بودUser Profile اعلانی Keycloak با سیاست پیش‌فرض، هر Attribute اعلام‌نشده را بی‌صدا دور می‌ریزد. کد قبلی یک Attribute تحت‌اللفظی authz.scope.* می‌ساخت، ولی Keycloak Wildcard در نام Attribute را پشتیبانی نمی‌کند — پس هیچ Attribute واقعی اعلام نشده بود. اکنون به‌ازای هر کلید Scope یک Attribute مشخص (authz.scope.region، authz.scope.branch، …) با دسترسی فقط-ادمین اعلام می‌شود.رفع شد
Claimهای Scope در توکن نبودندClient Scopeهای authz-scopes و iam-access به کلاینت‌ها متصل نبودند، پس Mapperها هرگز اجرا نمی‌شدند. اکنون در شروع کار Facade به‌صورت خودکار و تکرارپذیر (Idempotent) به همهٔ کلاینت‌ها متصل می‌شوند.رفع شد
مجوزهای Orders.* در توکن کاربر نبودندMapper تجمیع‌کنندهٔ Client Role روی کلاینت نبود؛ فقط Mapper نقش‌های Realm وجود داشت. اکنون oidc-usermodel-client-role-mapper اضافه شده است.رفع شد
نکتهٔ مهم هنگام Import مجدد Realm: کدِ Facade به‌صورت خودکار فقط برای کلاینت‌هایی Mapper نقش می‌سازد که خودشان Manifest ثبت می‌کنند (مثل order-service). برای کلاینت خودِ identity-facade هیچ Manifestی ثبت نمی‌شود، پس Mapper تجمیع آن باید از فایل Realm بیاید — که اضافه شده است (permission-client-role-aggregate در deploy/realm-company.json). اگر Realm را دستی ویرایش کردید یا نسخهٔ قدیمی وارد کردید، نبودِ این Mapper باعث می‌شود کاربران فقط نقش‌های Realm را ببینند و مجوزهای سرویس‌ها (Orders.*) در توکنشان نیاید. با GET /api/identity/me یا Decode توکن بررسی کنید.
اتصال Client Scopeها فرق دارد: برخلاف Mapper بالا، اتصال authz-scopes و iam-access به کلاینت‌ها توسط کد در هر شروعِ Facade خودکار و تکرارپذیر انجام می‌شود (در تست، پس از حذف دستی، با راه‌اندازی مجدد به هر ۸ کلاینت بازگشت). پس این بخش نیاز به اقدام دستی ندارد.
خودترمیمی: اتصال Client Scopeها فقط در فایل Realm نوشته نشده (چون Import با سیاست «نادیده گرفتن موجود» روی Realmهای قدیمی اثر ندارد). Facade در هر شروع، نبودِ اتصال را تشخیص داده و برطرف می‌کند. در تست، اتصال‌ها دستی حذف شدند و پس از راه‌اندازی مجدد، خودکار به هر ۸ کلاینت بازگشتند.

۵. ساخت کاربر همراه با نقش و Scope

یک درخواست، سه کار انجام می‌دهد: ساخت کاربر در Keycloak، نوشتن Attributeهای Scope، و عضویت در گروه نقش. اگر مرحلهٔ Scope شکست بخورد، کاربر ساخته‌شده بازگردانی (Rollback) و حذف می‌شود تا کاربر نیمه‌کاره نماند.

۵.۱ ساخت کامل کاربر

cat > new-user.json <<'EOF' { "username": "sara-tax", "email": "sara@company.local", "firstName": "سارا", "lastName": "مدیر", "enabled": true, "credentials": { "password": "SaraPass#1!", "temporary": false }, "assignments": [ { "role": "SeniorAccountant", "scopes": { "region": ["tehran-2"], "branch": ["b-3"] } } ] } EOF curl -s -X POST http://localhost:5080/api/identity/users \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json; charset=utf-8" \ --data-binary @new-user.json

پاسخ واقعی (HTTP 201 Created):

{ "id": "84b48d80-79b9-4a16-8fdb-b41dc1d7232c", "username": "sara-tax", "displayName": "سارا مدیر", "enabled": true, "attributes": {} }
چرا attributes در پاسخ خالی است؟ چون Attributeها پس از ساخت کاربر و در مرحلهٔ جداگانه نوشته می‌شوند و پاسخ ساخت، نمای کاربر را همان لحظهٔ ایجاد برمی‌گرداند. برای دیدن Attributeها از GET /users/{id}/scoped-access استفاده کنید.

با "temporary": true کاربر در اولین ورود مجبور به تغییر گذرواژه می‌شود (Recommended برای کاربران ساخته‌شده توسط ادمین).

۵.۲ پیام‌های خطای قابل‌فهم

همهٔ خطاهای اعتبارسنجی با HTTP 400 و ساختار استاندارد RFC 9110 با آدرس دقیق فیلد برمی‌گردند. نمونه‌های واقعی از تست:

الف) نقش وجود ندارد:

{ "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1", "title": "One or more validation errors occurred.", "status": 400, "errors": { "assignments[0].role": ["Role 'NoSuchRole' does not exist."] } }

ب) کلید Scope تعریف نشده یا غیرفعال است:

{ "status": 400, "errors": { "assignments[0].scopes.nonexistent-scope": ["Scope 'nonexistent-scope' is not defined or is inactive."] } }

ج) مقدار خالی:

{ "status": 400, "errors": { "assignments[0].scopes.region": ["Scope must have at least one value."] } }

د) Scope برای این نقش مجاز نیست (وقتی گروه authz.allowed-scopes = ["region","branch","cost-center"] دارد و customer خواسته شود):

{ "status": 400, "errors": { "assignments[0].scopes.customer": ["Scope 'customer' is not allowed for role 'SeniorAccountant'."] } }

ه) فیلدهای الزامی پروفایل ناقص است — این مورد در تست کشف و اضافه شد:

{ "status": 400, "errors": { "email": ["'email' is required by the identity provider's user profile; without it the user cannot sign in."], "firstName": ["'firstName' is required by the identity provider's user profile; without it the user cannot sign in."], "lastName": ["'lastName' is required by the identity provider's user profile; without it the user cannot sign in."] } }
چرا مورد «ه» اضافه شد: در User Profile این Realm، فیلدهای email، firstName و lastName برای نقش user الزامی‌اند. ساخت کاربر بدون آن‌ها با 201 موفق می‌شد، ولی کاربر بعداً هرگز نمی‌توانست وارد شود و خطای مبهم Account is not fully set up می‌گرفت. اکنون Facade فهرست فیلدهای الزامی را از خود Keycloak می‌خواند و قبل از ساخت کاربر، خطای field-level می‌دهد.

و) نام کاربری یا ایمیل تکراری:

{ "code": "validation_error", "message": "Failed to create user 'reza-tax': Failed to create user 'reza-tax': 409 {\"errorMessage\":\"User exists with same email\"}", "correlationId": "866b0fbd-..." }

۵.۳ به‌روزرسانی کاربر

curl -s -X PUT http://localhost:5080/api/identity/users/{userId} \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ -d '{"firstName":"سارا","lastName":"مدیر ارشد","enabled":true}'

به‌روزرسانی به‌صورت «بخوان، ادغام کن، بنویس» انجام می‌شود تا Attributeهای Scope پاک نشوند. برای تغییر گذرواژه از Admin Console یا Admin REST Keycloak استفاده کنید (این Endpoint گذرواژه را تغییر نمی‌دهد).

۶.۲ ساخت Scope جدید

cat > new-scope.json <<'EOF' { "key": "cost-center", "displayName": "مرکز هزینه", "description": "مرکز هزینه مالی برای فیلتر داده‌ها" } EOF curl -s -X POST http://localhost:5080/api/identity/scopes \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json; charset=utf-8" \ --data-binary @new-scope.json

ساخت یک Scope سه کار را خودکار انجام می‌دهد (تأییدشده در تست):
  1. Attribute scope.cost-center در گروه iam-scope-registry نوشته می‌شود.
  2. Mapper مربوط به Claim (authz-scope-cost-center) ساخته و به Client Scope authz-scopes اضافه می‌شود — بدون نیاز به راه‌اندازی مجدد.
  3. Attribute authz.scope.cost-center در User Profile اعلام می‌شود تا نوشتنش ممکن باشد.
پس بلافاصله می‌توانید آن را به کاربر اختصاص دهید و در توکن بعدی ببینید.
دو ایرادی که در این مسیر پیدا و رفع شد:
  • خطای ۵۰۰ هنگام ساخت Scope با توضیح فارسی: ستون GROUP_ATTRIBUTE.VALUE در Keycloak حداکثر ۲۵۵ بایت است. JSON توضیح با فرارِ \uXXXX شش‌برابر حجیم می‌شد (خطای ORA-12899). اکنون JSON فشرده نوشته می‌شود (کاراکترهای فارسی خام) و اگر باز هم بلند بود، بین چند مقدارِ همان Attribute چندمقداری شکسته و هنگام خواندن به هم چسبانده می‌شود.
  • Endpointها به دیتابیس Oracle منسوخ وصل بودند: این مسیرها جداول legacy را می‌خواندند در حالی که اعتبارسنجی از Keycloak می‌خواند؛ یعنی ساخت Scope عملاً هیچ اثری نداشت. اکنون هر دو سمت از iam-scope-registry کار می‌کنند.

۶.۳ ویرایش و غیرفعال‌سازی

curl -s -X PUT http://localhost:5080/api/identity/scopes/cost-center \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ -d '{"isActive": false}'

با isActive: false آن Scope برای تخصیص‌های جدید رد می‌شود («not defined or is inactive»)، ولی مقادیر قبلی کاربران پاک نمی‌شوند. برای حذف کامل، Attribute را از گروه رجیستری در Keycloak پاک کنید.

۶.۴ محدود کردن Scopeهای مجاز یک نقش

این کار با Attribute authz.allowed-scopes روی گروه همان نقش انجام می‌شود:

# از طریق Admin REST Keycloak curl -s -X PUT "$KEYCLOAK/admin/realms/company/groups/{groupId}" \ -H "Authorization: Bearer $KEYCLOAK_ADMIN_TOKEN" -H "Content-Type: application/json" \ -d '{"name":"SeniorAccountant","attributes":{"authz.allowed-scopes":["region","branch"]}}'
دو نکتهٔ عملی: ۱) اگر این Attribute تنظیم نشده باشد، همهٔ Scopeها برای آن نقش مجازند (رفتار باز). برای اعمال محدودیت حتماً آن را تنظیم کنید. ۲) چون PUT کل Attributeها را جایگزین می‌کند، Attributeهای دیگر را هم در بدنه نگه دارید. پس از تغییر، نتایج تا انقضای کش (حداکثر ۵ دقیقه) یا تا یک تغییر از طریق API که کش را Invalidate می‌کند، به‌روز نمی‌شوند.

۶.۵ کش و به‌روز بودن داده

دادهٔ رجیستری در دو لایه کش می‌شود: حافظهٔ محلی (L1) و Redis (L2) با عمر ۵ دقیقه. Redis باعث می‌شود چند نمونهٔ Facade کش یکدیگر را هم باطل کنند.

افزودن / حذف مجوز نقشبلافاصله باطل می‌شود

اسکریپت deploy/smoke-test.sh هر هفت گام جریان هدف را پشت‌سر هم اجرا و تأیید می‌کند (فقط curl و python لازم دارد):

۹. چک‌لیست محیط واقعی

  • گذرواژهٔ admin و همهٔ Secretهای کلاینت عوض شوند و از Vault خوانده شوند.
  • گرنت password روی کلاینت identity-facade بسته شود (directAccessGrantsEnabled: false) و ورود از طریق جریان استاندارد OIDC انجام شود.
  • همه‌چیز پشت HTTPS باشد و RequireHttpsMetadata فعال شود.
  • authz.allowed-scopes برای همهٔ نقش‌ها صریحاً تنظیم شود (نبودش یعنی «همه مجاز»).
  • Attributeهای Scope فقط توسط ادمین قابل نوشتن بمانند (User Profile Hardening در شروع کار اعمال می‌شود).
  • Redis برای کش مشترک بین نمونه‌ها فعال بماند.
  • پیش از استقرار، smoke-test.sh اجرا شود.
مواردی که آگاهانه باز مانده‌اند: اگر Keycloak در دسترس نباشد، رجیستری به فهرست پیش‌فرض Scopeها برمی‌گردد تا سیستم از کار نیفتد (رفتار باز). برای محیط واقعی سخت‌گیرانه‌تر، این رفتار باید به «رد کردن درخواست» تغییر کند. همچنین IAuditSink فعلاً هیچ‌کاره (Noop) است و رویدادهای امنیتی ثبت نمی‌شوند.

آخرین به‌روزرسانی این راهنما: پس از تست کامل روی استک docker (Keycloak، Oracle، Redis، Vault، Facade و order-service). همهٔ پاسخ‌های نشان‌داده‌شده خروجی واقعی اجرا هستند.
