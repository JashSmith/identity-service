راهنمای عملی یکپارچه‌سازی سرویس‌ها با Identity Facade

این سند مسیر کامل اتصال سرویس‌های بیرونی مانند Order Service و Product Service را به این پروژه توضیح می‌دهد. مرز استاندارد یکپارچه‌سازی، خود Identity Facade است؛ سرویس‌های مصرف‌کننده نباید آدرس Keycloak، نام Realm یا اعتبارنامهٔ مدیر را بدانند.

اصل معماری: Keycloak مالک کاربران، گذرواژه‌ها، نشست‌ها، نقش‌ها، صدور توکن و کلیدهای امضای JWT است. Facade فقط درخواست‌های احراز هویت را عبور می‌دهد، اطلاعات امن را ارائه می‌کند، مجوزهای سرویس‌ها را ثبت می‌کند و Discovery/JWKS را پروکسی می‌کند. Facade هیچ توکنی تولید نمی‌کند.

۳. اتصال هر سرویس جدید؛ مثال Order و Product

۳.۱ اطلاعاتی که هر Consumer لازم دارد

  1. یک Client محرمانه و یکتا در Keycloak؛ مانند order-service یا product-service.
  2. Client Secret در Secret Store یا متغیر محیطی سرور.
  3. فقط آدرس Facade؛ داخل Compose برابر http://identity-facade:5080.
  4. نام Permissionهای مخصوص خودش؛ مانند Orders.View و Products.Read.
  5. تنظیم اعتبارسنجی JWT با Authority برابر Facade.
  6. ثبت Manifest در زمان شروع برنامه.
در تنظیمات Consumer نباید Identity:Keycloak:BaseUrl، Realm، رمز مدیر یا تنظیمات Admin Keycloak وجود داشته باشد.

۳.۲ تنظیمات Consumer

{ "Identity": { "Authority": "http://identity-facade:5080", "Audience": "identity-facade" }, "PermissionRegistration": { "IdentityServer": "http://identity-facade:5080", "ClientId": "order-service", "ClientSecret": "از Secret Store خوانده شود" } }
builder.Services.AddCompanyAuthentication(options => { options.Authority = builder.Configuration["Identity:Authority"]!; options.Audience = "identity-facade"; options.RequireHttpsMetadata = !builder.Environment.IsDevelopment(); options.AcceptIssuerFromDiscovery = true; }); builder.Services.AddCompanyAuthorization();

AcceptIssuerFromDiscovery=true لازم است، چون Authority آدرس Facade است اما مقدار iss توکن واقعی همچنان Issuer متعلق به Keycloak است.

۴. ورود سرویس‌ها

۴.۱ ورود سرویس به سرویس (Client Credentials)

وقتی Order Service می‌خواهد بدون حضور کاربر به یک API محافظت‌شده دسترسی پیدا کند، از Client Credentials استفاده می‌کند. درخواست به Facade می‌رود و Facade آن را به Keycloak عبور می‌دهد.

curl -s -X POST http://localhost:5080/api/identity/auth/login \ -H 'Content-Type: application/x-www-form-urlencoded' \ -d 'grant_type=client_credentials' \ -d 'client_id=order-service' \ -d 'client_secret=order-service-development-only'

فقط فیلد access_token را در حافظهٔ موقت بخوانید و در هدر Bearer استفاده کنید؛ کل توکن را چاپ یا ذخیره نکنید.

TOKEN=$(curl -s -X POST http://localhost:5080/api/identity/auth/login \ -d 'grant_type=client_credentials' \ -d 'client_id=order-service' \ -d 'client_secret=order-service-development-only' \ | python3 -c "import json,sys; print(json.load(sys.stdin)['access_token'])") curl -s http://localhost:5180/api/orders -H "Authorization: Bearer $TOKEN"
Service Account نمونه فقط مجوز Identity.Permissions.Register دارد. بنابراین ثبت Manifest مجاز است، اما دسترسی خواندن سفارش‌ها به‌طور خودکار به آن داده نمی‌شود؛ باید Permission صریحاً به Client یا کاربر اختصاص داده شود.

۴.۲ ورود کاربر

در محیط توسعهٔ فعلی کاربر admin با گذرواژهٔ admin وجود دارد. در محیط واقعی این مقادیر باید تغییر کنند و درخواست باید فقط روی HTTPS ارسال شود.

curl -s -X POST http://localhost:5080/api/identity/auth/login \ -d 'grant_type=password' \ -d 'client_id=identity-facade' \ -d 'client_secret=facade-development-only' \ -d 'username=admin' \ -d 'password=admin'

رمز کاربر فقط باید به Endpoint ورود ارسال شود. Secret کلاینت را هرگز در JavaScript مرورگر قرار ندهید.

۵. ثبت Permissionهای سرویس

هر سرویس عملیات خود را با [RequirePermission] علامت‌گذاری می‌کند. کتابخانهٔ Company.Identity.PermissionRegistration در زمان شروع، Assembly را اسکن، Manifest را Hash و با Client Credentials به Facade ارسال می‌کند.

public static class ProductPermissions { public const string Read = "Products.Read"; public const string Create = "Products.Create"; } public sealed class ProductService { [RequirePermission(ProductPermissions.Read)] public IReadOnlyCollection<ProductDto> List() => ...; [RequirePermission(ProductPermissions.Create)] public ProductDto Create(...) => ...; }
builder.Services.AddPermissionRegistration(o => { o.IdentityServer = new Uri( builder.Configuration["PermissionRegistration:IdentityServer"]!); o.ServiceName = "product-service"; o.ServiceVersion = "1.0.0"; o.ClientId = builder.Configuration["PermissionRegistration:ClientId"]; o.ClientSecret = builder.Configuration["PermissionRegistration:ClientSecret"]; o.MaximumRetries = 8; });

Facade برای هر Permission یک Realm Role در Keycloak ایجاد می‌کند. شکست ثبت، شروع سرویس را متوقف نمی‌کند و با Backoff تصاعدی دوباره امتحان می‌شود. Permission حذف‌شده از Manifest حذف خودکار نمی‌شود و فقط در کاتالوگ Facade Deprecated می‌شود.

۶. Well-known، Discovery، JWKS و اطلاع از کلیدها

سرویس مصرف‌کننده نباید مسیر Keycloak را حدس بزند. Discovery استاندارد را از Facade بخواند:

curl -s http://localhost:5080/.well-known/openid-configuration | python3 -m json.tool curl -s http://localhost:5080/api/identity/oidc/jwks | python3 -m json.tool

Facade سند Discovery را از Keycloak عبور می‌دهد و فقط jwks_uri را به مسیر خودش تغییر می‌دهد. Issuer، Token Endpoint و سایر مقادیر متعلق به توکن واقعی Keycloak باقی می‌مانند.

{ "issuer": "http://keycloak:8080/realms/company", "token_endpoint": "http://keycloak:8080/realms/company/protocol/openid-connect/token", "introspection_endpoint": "http://keycloak:8080/realms/company/protocol/openid-connect/token/introspect", "end_session_endpoint": "http://keycloak:8080/realms/company/protocol/openid-connect/logout", "jwks_uri": "http://localhost:5080/api/identity/oidc/jwks" }

کتابخانهٔ JWT کلیدها را Cache می‌کند و در صورت مشاهدهٔ kid جدید، JWKS را دوباره می‌خواند. Rotation باید kid جدید بسازد؛ کلید قبلی در Grace Period برای اعتبارسنجی باقی می‌ماند. کلید خصوصی هرگز در تنظیمات، API، لاگ یا Redis قرار نمی‌گیرد.

۷. دریافت اطلاعات کاربر، Introspect، خروج و بستن نشست

۷.۱ اطلاعات کاربر جاری

curl -s http://localhost:5080/api/identity/me \ -H "Authorization: Bearer $ACCESS_TOKEN"

این پاسخ sub، نام کاربری، Roles، Permissions و sid را از JWT اعتبارسنجی‌شده می‌خواند. برای دادهٔ مدیریتی نیز این مسیرها وجود دارند:

GET /api/identity/users GET /api/identity/users/{id} GET /api/identity/users/{id}/roles GET /api/identity/users/{id}/permissions GET /api/identity/roles GET /api/identity/permissions?serviceId=order-service

این مسیرها به‌ترتیب به مجوزهای Identity.Users.Read، Identity.Roles.Read و Identity.Permissions.Read نیاز دارند.

۷.۲ Introspection

برای JWT، اعتبارسنجی محلی روش عادی و سریع است. زمانی از Introspection استفاده کنید که Backend به پاسخ فعال/غیرفعال بودن توکن از Keycloak نیاز دارد.

curl -s -X POST http://localhost:5080/api/identity/auth/introspect \ -d "token=$ACCESS_TOKEN" \ -d 'client_id=identity-facade' \ -d 'client_secret=facade-development-only'

اگر پاسخ active=false بود، عملیات را رد کنید. توکن را لاگ نکنید.

۷.۳ Refresh

curl -s -X POST http://localhost:5080/api/identity/auth/refresh \ -d 'client_id=identity-facade' \ -d 'client_secret=facade-development-only' \ -d "refresh_token=$REFRESH_TOKEN"

Facade نوع Grant را روی refresh_token تنظیم و درخواست را به Keycloak می‌فرستد.

۷.۴ Logout و بستن نشست

curl -i -X POST http://localhost:5080/api/identity/auth/logout \ -d "refresh_token=$REFRESH_TOKEN" \ -d 'client_id=identity-facade' \ -d 'client_secret=facade-development-only'

Facade ابتدا Logout و در صورت نیاز Revoke را روی Keycloak صدا می‌زند. پس از موفقیت، Session یا Cookie محلی برنامه را هم پاک کنید. در Client Credentials نشست کاربری وجود ندارد؛ فقط Access Token را از حافظه حذف و برای درخواست بعدی توکن جدید بگیرید.

Access Token خودبسنده تا زمان انقضا ممکن است از نظر امضایی معتبر بماند. برای قطع سریع دسترسی، سیاست کوتاه‌مدت Access Token و در موارد لازم Introspection فعال داشته باشید؛ حذف توکن از حافظه به‌تنهایی Logout سمت سرور نیست.

۸. ساخت نقش و اعطای دسترسی

۸.۱ مدل Permission و Role

  • Permission: نام یک عملیات، مانند Orders.View.
  • Realm Role: در این پروژه مکانیزم Keycloak برای ذخیره و اختصاص همان Permission است.
  • Assignment: عملیات صریح مدیر برای اتصال Role به User یا Service Account.

۸.۲ گرفتن Token مدیر Keycloak در توسعه

KC_ADMIN_TOKEN=$(curl -s -X POST \ http://localhost:8080/realms/master/protocol/openid-connect/token \ -d 'grant_type=password' -d 'client_id=admin-cli' \ -d 'username=admin' -d 'password=admin-development-only' \ | python3 -c "import json,sys; print(json.load(sys.stdin)['access_token'])")

این مسیر فقط برای توسعه است. در تولید از Client محرمانه با حداقل مجوز Admin API استفاده کنید.

۸.۳ اختصاص Permission به کاربر

curl -s 'http://localhost:8080/admin/realms/company/users?username=admin&exact=true' \ -H "Authorization: Bearer $KC_ADMIN_TOKEN" curl -s http://localhost:8080/admin/realms/company/roles/Orders.View \ -H "Authorization: Bearer $KC_ADMIN_TOKEN" curl -i -X POST \ http://localhost:8080/admin/realms/company/users/<USER_ID>/role-mappings/realm \ -H "Authorization: Bearer $KC_ADMIN_TOKEN" \ -H 'Content-Type: application/json' \ --data '[{"id":"<ROLE_ID>","name":"Orders.View"}]'

یا در Console مسیر company → Users → admin → Role mapping → Orders.View را انجام دهید. بعد از Assignment باید کاربر دوباره Login یا Refresh کند؛ Token قبلی خودکار تغییر نمی‌کند.

۸.۴ ساخت نقش تجاری

curl -i -X POST http://localhost:8080/admin/realms/company/roles \ -H "Authorization: Bearer $KC_ADMIN_TOKEN" \ -H 'Content-Type: application/json' \ --data '{"name":"OrderManager","description":"مدیریت سفارش‌ها"}'

سپس Permissionهای لازم را صریحاً به آن Role به‌صورت Composite اضافه و آن را به کاربر اختصاص دهید. هیچ Role بیرونی نباید بدون Mapping صریح به Role privileged داخلی تبدیل شود.

۹. فراخوانی استاندارد API؛ مثال دریافت سفارش‌ها

  1. Discover: Consumer با Authority برابر Facade، Discovery و JWKS را می‌گیرد.
  2. Acquire: توکن واقعی Keycloak را از Login Facade می‌گیرد.
  3. Validate: API مقصد امضا، Issuer، Audience، Lifetime و نوع توکن را با JWKS Cacheشده بررسی می‌کند.
  4. Authorize: دقیقاً Permission مسیر، مانند Orders.View، بررسی می‌شود.
  5. Call: درخواست با Authorization: Bearer و روی TLS ارسال می‌شود.
  6. Interpret: پاسخ 401 یعنی احراز هویت نامعتبر/منقضی؛ 403 یعنی توکن معتبر است ولی Permission ندارد.
  7. Recover: برای 401 توکن را Refresh یا دوباره Login کنید؛ برای 403 صرفاً Retry نکنید، Assignment را اصلاح کنید.
using System.Net.Http.Headers; public sealed class OrdersClient(HttpClient http) { public async Task<HttpResponseMessage> GetOrdersAsync( string accessToken, CancellationToken ct) { using var request = new HttpRequestMessage(HttpMethod.Get, "/api/orders"); request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", accessToken); return await http.SendAsync(request, ct); } }

در ASP.NET می‌توان از BearerTokenDelegatingHandler برای عبور دادن Bearer ورودی به سرویس پایین‌دستی مورد اعتماد استفاده کرد. این کار فقط در مرز اعتماد مشخص و کنترل‌شده انجام شود.

۱۰. تست کامل Order Service

# دریافت توکن مدیر از Facade ADMIN_RESPONSE=$(curl -s -X POST http://localhost:5080/api/identity/auth/login \ -d 'grant_type=password' -d 'client_id=identity-facade' \ -d 'client_secret=facade-development-only' \ -d 'username=admin' -d 'password=admin') ADMIN_TOKEN=$(echo "$ADMIN_RESPONSE" | python3 -c "import json,sys; print(json.load(sys.stdin)['access_token'])") # بررسی ثبت ۱۰ Permission curl -s 'http://localhost:5080/api/identity/permissions?serviceId=order-service' \ -H "Authorization: Bearer $ADMIN_TOKEN" | python3 -m json.tool # پس از اختصاص Orders.View به admin و Login مجدد: curl -i http://localhost:5180/api/orders \ -H "Authorization: Bearer $ADMIN_TOKEN" # قبل از Assignment: 403 # پس از Assignment و گرفتن Token جدید: 200

ده عملیات نمونه شامل سفارش، فاکتور، ارسال، Refund و گزارش است. مسیر کامل آن‌ها در http://localhost:5180/scalar قابل مشاهده است.

۱۱. چک‌لیست تولید

  • HTTPS و RequireHttpsMetadata=true.
  • تعویض همهٔ Password، Client Secret، Vault Token و Admin پیش‌فرض.
  • نگهداری Secretها در Secret Manager و نه Git یا appsettings عمومی.
  • عدم ثبت Password، Access/Refresh Token، Private Key و Vault Secret در Log.
  • استفاده از Access Token کوتاه‌عمر و سیاست روشن Refresh/Revoke.
  • بررسی دقیق Role Mapping و عدم ارتقای خودکار نقش خارجی.
  • تست Rotation، تغییر kid، JWKS Refresh، Grace Period و Rollback.
